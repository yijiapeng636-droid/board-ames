## ADDED Requirements

### Requirement: 完整位置历史
系统 MUST 保存包含全部棋子类型、颜色、位置和 sideToMove 的稳定 Position key，并保留产生该位置的着法信息。

#### Scenario: 同盘不同走方
- **当** 棋子布局相同但轮到不同方行动
- **那么** 两个局面的 Position key 不相同

### Requirement: 可审计着法分类
系统 MUST 为将、杀、捉、兑、献、拦、闲及规则要求的组合效果保存 `effects`、`primaryEffect` 和判定证据，禁止使用简单优先级冒充完整分类。

#### Scenario: 一着多重作用
- **当** 一手棋同时形成多个规则效果
- **那么** 分类结果保留全部效果、最终主要类别、相关棋子与选择该类别的规则证据

### Requirement: 循环识别与独立裁决
系统 MUST 先识别循环起止位置和双方循环着法，再由独立 Adjudicator 输出 `none`、`mustChange`、`draw` 或 `loss`，禁止以“相同棋盘三次即和”替代棋例。

#### Scenario: 发现重复局面
- **当** Position History 中出现重复循环
- **那么** 系统提取完整循环区间、分类双方着法并明确谁 MUST 变着、原因和继续不变的后果

### Requirement: 2020规则资料门禁
复杂棋例 MUST 逐条依据经项目提供或确认的《中国象棋协会审定〈象棋竞赛规则（2020版）〉》实现，每个测试 MUST 包含 `ruleReference`；资料或覆盖不足时禁止声称完整规则。

#### Scenario: 规则资料未提供
- **当** 项目无法读取规则正文或对应棋例图
- **那么** Phase 4 标记为阻断，不开始象棋 AI，最终报告列出未实现条款和棋例

#### Scenario: 转换规则棋例
- **当** 实现第六、八、九章中的可程序化棋例
- **那么** 测试包含初始局面、循环着法、期望分类、期望裁决和准确条款编号
